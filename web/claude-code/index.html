1

Cómo trabaja un agente

20 minutos · 0:10 a 0:30

Un agente repite un ciclo: reúne contexto, actúa y verifica, hasta que la tarea está hecha. Lo avanzado no son trucos: es controlar cada paso del ciclo.

  • LeeCLAUDE.md, archivos, issues, documentación
  • PlaneaDivide la tarea; en modo plan, te propone antes de actuar
  • ActúaEdita archivos y corre comandos
  • VerificaPruebas, métricas, capturas: evidencia
  • EntregaCommit, PR y un resumen

Las cinco palancas de hoy

  • MemoriaQué sabeCLAUDE.md y .claude/rules/: se cargan en cada sesión.
  • HabilidadesQué sabe hacerSkills: /experimento, /publicar-modelo…
  • EquipoCon quién trabajaSubagentes con su propio contexto: explorador-datos, revisor-ml.
  • ReglasQué no puede hacerPermisos y hooks: se cumplen siempre, no dependen de que Claude se acuerde.
  • ConexionesQué alcanzaMCP (documentación, navegador) y GitHub (@claude, revisión).

Modos de permiso y atajos

Shift+Tab cambia el modo: manual (pregunta antes de editar o correr comandos), aceptar ediciones, plan (solo lee y propone) y auto (un segundo modelo revisa cada acción por ti). Esc detiene a Claude sin perder el contexto; Esc Esc o /rewind vuelve a un punto anterior, archivos incluidos. @archivo le muestra un archivo; /context muestra qué ocupa su memoria y /clear la limpia entre tareas.

Estoy empezando en este repositorio y todavía no quiero cambiar nada.
Explícame en español, citando las rutas de los archivos:

2. Qué archivos se generan y cuáles se editan a mano.
3. Qué comandos verifican que todo funciona. Córrelos y muéstrame la salida.

Qué debe pasar: Claude lee CLAUDE.md, recorre scripts/ y web/, corre las pruebas y la paridad, y te devuelve un mapa del proyecto. Ningún archivo cambia.

2

El prompt profesional

25 minutos · 0:30 a 0:55

Un buen prompt se parece a un buen issue: cualquiera lo podría resolver sin preguntarte nada. Tiene seis partes.

  1. ContextoDónde estamos y qué ya existe.Vamos a resolver el issue #3. Lee CLAUDE.md y @docs/ESPECIFICACION.md.
  2. ObjetivoEl resultado, en una frase.Publicar el primer modelo de mi proyecto.
  3. RestriccionesQué no tocar y qué usar.Sin columnas sensibles. No cambies el diseño de web/.
  4. Criterios de aceptaciónUna lista que se responde con sí o no.Mejora el MAE de la línea base en al menos 10 %.
  5. VerificaciónEl comando o la evidencia que prueba que está hecho.Muéstrame pytest y el «OK» de la paridad.
  6. EntregableCómo debe quedar el trabajo.Rama feature/primer-modelo y un PR que cierre el issue.
Así no

haz mi modelo y súbelo

Así sí

Resuelve el issue #3 (lee CLAUDE.md). Compara los 4 modelos con /experimento y recomiéndame uno. Sin columnas sensibles. Debe mejorar el MAE de la línea base en 10 %. Muéstrame la tabla y el OK de la paridad. No publiques: eso lo hago yo.

Cuatro hábitos que separan al principiante del profesional

  • Explora, planea y después programa. Usa el modo plan cuando el cambio toca varios archivos o no conoces el código. Si el cambio cabe en una frase, no hace falta.
  • Pide evidencia, no promesas. «Listo» no basta: la salida de las pruebas, la tabla o la captura.
  • Corrige temprano. Si a la segunda corrección sigue mal, /clear y un prompt mejor, con lo que aprendiste.
  • Una sesión, una tarea. Mezclar temas llena la memoria de ruido. /clear entre tareas distintas.
P2

Que Claude te entreviste y escriba la especificación

Modo planTerminalNube

Antes de programar tu proyecto final. Las preguntas difíciles salen antes de escribir código.

Quiero adaptar esta plantilla a mi proyecto final: [tu pregunta y tus datos en dos líneas].
Antes de tocar código, entrevístame con preguntas de opción múltiple, una por una, sobre lo difícil:
la columna objetivo, qué columnas usar y cuáles excluir (por ética o por fuga de datos), cómo voy a medir el éxito frente a la línea base y para qué NO debe usarse el modelo.
No hagas preguntas obvias.
Al terminar, escribe docs/ESPECIFICACION.md con: pregunta, enlace a los datos, objetivo, columnas, exclusiones con su motivo, criterio de éxito y lo que queda fuera de alcance. Espera mi aprobación.

Qué debe pasar: Varias preguntas con opciones y, al final, un docs/ESPECIFICACION.md corto que tú apruebas o corriges.

P3

Enséñale tu proyecto a Claude (CLAUDE.md)

TerminalNube

Después de aprobar la especificación. Todo lo que pongas en CLAUDE.md, Claude lo lee en cada sesión.

Con docs/ESPECIFICACION.md, actualiza solo la sección «Proyecto» de CLAUDE.md: pregunta, enlace a los datos, objetivo, columnas, exclusiones con su motivo y el comando exacto para entrenar.
No toques las demás secciones y deja CLAUDE.md por debajo de 80 líneas.

P5

Un issue que se puede verificar

GitHubTerminalNube

Toda tarea empieza en un issue: queda escrita, tiene criterios de aceptación y la cierra un PR.

Crea un issue en GitHub con la plantilla «Tarea» para: «Entrenar y publicar el primer modelo de mi proyecto».
Contexto: lo que dice docs/ESPECIFICACION.md.
Criterios de aceptación verificables: el modelo mejora el MAE de la línea base en al menos 10 %, no usa columnas sensibles, la prueba de paridad termina en OK y el README tiene la tabla de métricas.

Dame el número y el enlace del issue.

Qué debe pasar: Un issue nuevo con contexto, criterios con casillas y verificación. Si Claude no puede crearlo, créalo tú en GitHub con la plantilla Tarea.

P6

Del issue al plan, con experimentos

Modo planTerminalNube

El corazón de la clase: Claude investiga, compara con evidencia y tú decides.

Vamos a resolver el issue #[número].
1. Lee el issue y CLAUDE.md y propón un plan corto: comandos, archivos que cambian y riesgos. Espera mi OK.
2. Crea la rama feature/primer-modelo.

P8

Revisión independiente antes de fusionar

SubagenteTerminalNube

Quien escribió el código no debería ser quien lo califica. El revisor no vio cómo se hizo: solo juzga el resultado.

Usa el subagente revisor-ml para revisar mi rama contra main antes de fusionar el PR #[número].
Solo hallazgos que cambien una conclusión o rompan algo.
Después corrige los 🔴, vuelve a correr las pruebas y sube los cambios a la misma rama.

Qué debe pasar: Un informe con 🔴 y 🟡, cada hallazgo con su evidencia. También puedes escribir @ y elegir revisor-ml (agent).

P9

Crea tu propia skill

SkillTerminalNube

Cuando escribes el mismo prompt por tercera vez, conviértelo en skill.

Crea una skill de proyecto en .claude/skills/preguntas-sustentacion/SKILL.md que lea el proyecto (CLAUDE.md, README, docs/experimentos.md y node scripts/resumen_modelo.js) y genere las 8 preguntas más difíciles que me haría un jurado sobre mi modelo, ordenadas de menor a mayor dificultad, cada una con una pista de dónde está la respuesta, pero sin la respuesta.
Que solo la pueda invocar yo (disable-model-invocation: true) y que no edite archivos.
Pruébala y muéstrame el resultado.

Qué debe pasar: Un archivo SKILL.md nuevo y, al escribir /preguntas-sustentacion, ocho preguntas para preparar tu sustentación.

P10

Una regla que se cumple siempre (hook)

HookTerminal

Lo que está en CLAUDE.md es una instrucción: Claude puede olvidarla. Un hook es código: se cumple siempre.

Agrega a .claude/settings.json un hook Stop que, si en este turno cambiaste archivos de scripts/ o tests/, corra python -m pytest tests/ -q y no te deje terminar mientras fallen (exit 2 con el error).
Que no entre en un ciclo infinito (revisa stop_hook_active).
Explícame cómo lo probaste y cómo lo apago con /hooks si me estorba.

Qué debe pasar: Un hook nuevo y una prueba: Claude rompe una prueba a propósito, el hook lo detiene y Claude la arregla antes de terminar.

5

Conexiones: MCP y Claude dentro de GitHub

25 minutos · 2:05 a 2:30

MCP (Model Context Protocol) conecta a Claude con otros sistemas: documentación, navegadores, bases de datos, GitHub. Cada servidor le da herramientas nuevas.

Servidores MCP

  • claude-code-docs: ya está en .mcp.json, así que todos los que clonan el repositorio lo tienen. Revisa su estado con /mcp.
  • Playwright (navegador; solo terminal y con Node.js). Se agrega en la terminal, fuera de Claude: 
    claude mcp add playwright -- npx -y @playwright/mcp@latest
  • GitHub (opcional): claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --header "Authorization: Bearer [tu token]". El token es tuyo: nunca va en .mcp.json ni en un commit. Para issues y PR también basta con gh.

MCPTerminal

Claude dentro de GitHub

El kit trae tres flujos en .github/workflows/: Pruebas (corre pytest y la paridad en cada PR, sin secretos), Claude (responde cuando escribes @claude) y Revisión de Claude (deja comentarios en las líneas con errores de cada PR). Los dos últimos necesitan una credencial:

  1. En la terminal: abre claude en tu repositorio y escribe /install-github-app. Instala la app de Claude y guarda el secreto por ti.
  2. A mano (desde la nube o el navegador): instala la app en github.com/apps/claude y, en Settings→Secrets and variables→Actions, crea CLAUDE_CODE_OAUTH_TOKEN (lo genera claude setup-token con tu plan) o ANTHROPIC_API_KEY (clave de la Console).
  3. Protege main (opcional, muy profesional): Settings→Rules→Rulesets, exige pull request y el check Pruebas para fusionar.

¿Trabajas en la nube? Los PR que abre una sesión de claude.ai/code tienen Auto-fix: Claude vigila el PR y corrige las pruebas que fallan y los comentarios de revisión.

6

Escala y seguridad

15 minutos · 2:30 a 2:45

Cuando Claude trabaja más tiempo sin ti, importan más dos cosas: que tenga una forma de verificar, y que no pueda hacer daño.

Más de un Claude a la vez

  • Subagentes en paralelo dentro de una sesión (P15).
  • Worktrees: claude --worktree experimento-a y, en otra terminal, claude --worktree experimento-b. Cada uno trabaja en su copia y su rama.
  • Nube: varias sesiones en claude.ai/code, cada una en su rama; o desde la terminal, claude --cloud "tu tarea".
P15

Dos experimentos en paralelo

SubagentesTerminalNube

Cada subagente trabaja en su propio contexto y en su propia carpeta: no se pisan.

Lanza dos subagentes en paralelo. Cada uno entrena con scripts/entrenar.py en su propia carpeta de experimentos/:
uno con [columnas A] y otro con [columnas B]. Que no escriban en docs/.
Cuando terminen, consolida una tabla comparativa en docs/experimentos.md y recomienda una combinación, con su justificación en una frase.

Qué debe pasar: Dos entrenamientos al mismo tiempo, una sola tabla y una recomendación.

P16

Una meta que Claude persigue solo (/goal)

TerminalNube

Claude sigue trabajando, turno tras turno, hasta que la condición se cumple.

/goal python -m pytest tests/ -q pasa, la prueba de paridad termina en OK y el README explica cada columna usada y cada columna excluida con su motivo

Qué debe pasar: Varios turnos seguidos sin que intervengas, hasta que la condición se cumple. Ojo: si la meta fuera solo «baja el MAE», el agente podría colarse una fuga de datos. Pon la meta en lo verificable y las reglas en CLAUDE.md.

P17

Claude como herramienta de línea de comandos

Terminal

Con -p, Claude responde una vez y termina: así se usa en scripts y en GitHub Actions.

claude -p "Resume en 5 viñetas qué cambió en el último commit y si hay algún riesgo para el modelo publicado"

Qué debe pasar: Una respuesta en la terminal, sin sesión interactiva. Agrega --output-format json para leerla desde un programa.

Seguridad y ética, sin negociar

  • Los secretos no viajan en prompts ni en commits. Van en GitHub Secrets o en variables de entorno. El kit le prohíbe a Claude leer .env.
  • El texto de afuera puede traer instrucciones. Un issue, una página web o un CSV pueden decir «ignora tus reglas». Por eso @claude solo responde a quien tiene permiso de escritura, y tú revisas cada diff.
  • Tú respondes por tu código. Revisa lo que Claude escribió antes de fusionar; si no lo entiendes, pregúntale hasta entenderlo.
  • Declara el uso de IA. La plantilla de PR trae la sección «Uso de IA»: qué hizo Claude y qué revisaste tú.
  • Cuida tu cuota. /usage muestra cuánto llevas; /clear entre tareas y prompts concretos gastan menos.

Si algo falla

«Ignoring permissions.allow entries… this workspace has not been trusted»
Abre claude una vez en la carpeta, sin -p, y acepta el diálogo de confianza. Hasta entonces Claude te pide permiso para todo.
Los hooks no hacen nada o muestran «bash: command not found»
En Windows, instala Git for Windows y abre una terminal nueva. Revisa con /hooks que estén cargados. Los cambios a .claude/settings.json se aplican al abrir una sesión nueva.
Claude no encuentra /experimento o los subagentes
Abre Claude en la raíz del repositorio (donde está CLAUDE.md) y escribe /skills. Si acabas de traer el kit, empieza una sesión nueva.
«No module named pandas» o «No module named pytest»
Corre python -m pip install -r requirements.txt pytest en la terminal, o pídeselo a Claude. En la nube lo hace el hook al iniciar la sesión.
@claude no responde en GitHub
Revisa tres cosas: la app de Claude instalada en el repositorio, el secreto CLAUDE_CODE_OAUTH_TOKEN o ANTHROPIC_API_KEY en Actions, y que el archivo .github/workflows/claude.yml esté en main. El error aparece en la pestaña Actions.
En la nube, gh issue create o gh pr create devuelven 403
En claude.ai/code esos comandos de gh no funcionan. Claude puede usar la API de GitHub (gh api) o el botón Create PR de la sesión. Si no, crea el issue tú en GitHub.
Se me acabó la cuota de uso
Mira /usage. Mientras se renueva, trabaja en pareja con alguien y sigue leyendo los diffs y las revisiones. Para ahorrar: /clear entre tareas, prompts concretos y un modelo más pequeño con /model para tareas simples.
